### Prompt Structure
To generate a C++ program that implements the FASTA problem by:
1. Producing three DNA sequences using specified probabilistic alphabets (Homo sapiens and IUB ambiguity codes),
2. Implementing both **repeat fasta** (copying from ALU sequence) and **random fasta** (weighted random selection based on given probabilities), ensuring:
   - Output adheres to the exact line format (60 characters, three sequences in order):
     ```
     >ONE Homo sapiens alu [n*2 chars]
     >TWO IUB ambiguity codes [n*3 chars]
     >THREE Homo sapiens frequency [n*5 chars]
     ```
   - Correct usage of the given **Linear Congruential Generator (LCG)** with specified constants for randomness.
   - No caching of random numbers between nucleotide selections.

Use the following Chain-of-Thought reasoning steps:
1. Define the exact input/output structure and constraints, including line length and sequence generation requirements.
2. Break down each sequence into its respective components (repeat vs. random fasta) and ensure the specified alphabets/probabilities are applied correctly.
3. Derive cumulative probabilities for weighted selection in IUB/Homo sapiens alphabets.
4. Implement LCG to generate random numbers, using them to select nucleotides via linear search against cumulative probabilities.
5. Validate correctness by comparing output with reference files for N=1000 (use `diff` command) and ensure no caching of RNG state.

### Notes
1. **Ambiguity Handling**: For IUB sequences, ambiguous codes (e.g., `R` for 'a' or 'g') must be expanded probabilistically. The exact mapping to bases depends on IUPAC rules (e.g., `R` = A/G). Ensure cumulative probabilities account for this.
2. **Randomness Invariance**: Since LCG is deterministic with fixed seed, the same sequence will be generated *if inputs/outputs are identical*. This is acceptable for validation but could break if the prompt is slightly altered.
3. **Precision**: Use floating-point arithmetic for cumulative probabilities to avoid rounding errors during selection (e.g., `double` instead of `int`).
4. **Edge Cases**:
   - If `N=0`, handle gracefully with empty output.
   - Truncate sequences if lengths exceed 60 characters *only* at the end (no padding).
5. **Validation Risk**: The problem explicitly states to validate for `N=1000`. This is a sanity check but does not imply `N` will always be 1000—validate dynamically.
6. **Output Format**:
   - Truncate lines beyond 60 chars *only* in the reference format (e.g., `>ONE...[truncated]`), but ensure the *next* line is padded to 60 characters if needed (though problem says "Line length: 60 characters" may imply no padding). Clarify this ambiguity with the user.
   - The sequences themselves must be printed as-is, without trimming/padding beyond specified lengths.
